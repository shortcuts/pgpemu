Prototype task for the BLE Companion Control feature (see .scratch/ble-companion-control/issues/08-app-screen-coverage-prototype.md): map the ~15 UART commands onto a rough screen layout (live status view vs explicit action vs settings toggle), and decide how destructive actions (secrets reset, restart) get confirmed in-app.

Resolved design (HTML wireframe prototype produced, throwaway, no app module exists yet to attach it to): single scrolling screen, not tabbed, sections ordered by risk/frequency — read-only Status → Device Profiles (autospin/autocatch toggles) → Settings (advertising toggle, max connections, save) → Diagnostics (stats/task-list/client-state dumps, disconnect-all) → Danger zone pinned last (reset secrets, restart). GET_* opcodes back read-only cards; TOGGLE_*/ADVERTISE_* opcodes are toggles; SET_MAX_CONNECTIONS is a stepper; SAVE_SETTINGS/CYCLE_LOG_LEVEL/RESET_CLIENT_STATES are explicit tap actions; RESET_SECRETS and RESTART are danger-zone actions. Destructive-action confirmation uses a bottom sheet with a plain-language consequence line plus a type-to-confirm text gate (type "RESET"/"RESTART"), not a plain Cancel/Confirm dialog, since both actions are silent and irreversible over BLE.
