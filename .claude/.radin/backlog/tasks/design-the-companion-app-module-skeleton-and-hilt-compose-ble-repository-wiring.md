Design decision for the BLE Companion Control feature (see .scratch/ble-companion-control/issues/09-app-module-skeleton.md): lay out the package/module skeleton for the single-module Companion App — package structure, where the BLE repository is provided (Hilt module), how Compose screens observe connection/command state, and what locationjoystick conventions carry over vs get dropped as overkill.

Depends on the "Decide Android BLE library and Companion App connection-manager architecture" entry — this skeleton wires up the repository interface that decision defines.

Resolved design: single-module, light package split — `ble/` (repository interface+impl, ConnectionState, ResponseFrame, opcode constants), `ui/` (single screen + DeviceViewModel), `di/BleModule.kt` (Hilt, `@Binds` the repository as a singleton, carrying over locationjoystick's `di/XModule.kt` naming convention). One `DeviceViewModel`, not per-section, exposing a single UI state collected via `collectAsStateWithLifecycle`. Testing: carry over locationjoystick's `core/testing` fake convention now (not deferred) — a `FakeBleControlRepository` implementing the repository interface. Dropped as overkill: locationjoystick's feature-module/`api`+`impl` split and multi-module Gradle structure — this app is one module, one repository, one screen.
