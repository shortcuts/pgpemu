Design decision for the BLE Companion Control feature (see .scratch/ble-companion-control/issues/06-android-ble-architecture.md): decide the connection-manager shape for the Companion App — repository pattern, its scan→connect→bond→discover→ready state machine, and how Command/Response round-trips surface to the UI layer.

Depends on the "Research Android BLE central APIs and libraries" entry — this design is built directly on the Nordic BLE library it recommends.

Resolved design: interface + impl split — `BleControlRepository` (interface) / `NordicBleControlRepository` (impl, built on Nordic's `ble`/`ble-ktx`). Connection state is an explicit sealed `ConnectionState`: `Idle`, `Scanning`, `Connecting`, `Bonding`, `DiscoveringServices`, `Ready`, `Disconnected(reason)`, `Error(reason)`, exposed as one `StateFlow`. Command/Response surface is `suspend fun sendCommand(opcode: Int, payload: ByteArray): Result<ResponseFrame>` — one call per round trip, not a raw Flow, since firmware is strictly one-command-at-a-time. Reconnect policy is manual only, no automatic retry loop. Scan matches by the existing PGP advertised name, then checks the Control Service UUID is present post-discovery (else `Error("device not migrated")`). Fits the single-module architecture — one repository interface/impl pair, no new module boundary.
