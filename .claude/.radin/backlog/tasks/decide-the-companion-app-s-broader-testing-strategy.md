Design decision for the BLE Companion Control feature (see .scratch/ble-companion-control/issues/12-companion-app-testing-strategy.md): beyond the `FakeBleControlRepository` unit-test seam, does the app need BLE-mock/integration-level testing (mirroring locationjoystick's MockK/Turbine conventions) for the connection-manager's state machine, or is unit coverage + AGENTS.md's existing on-device integration-test bar sufficient?

Depends on the "Design the Companion App module skeleton and Hilt/Compose/BLE-repository wiring" entry — the fake repository it builds is what the unit-test coverage here uses.

Resolved decision: unit tests + real on-device testing, no BLE-mock/fake-GATT layer. `DeviceViewModel` is unit-tested against `FakeBleControlRepository` for UI-state derivation, command dispatch, and error surfacing. Integration coverage is real on-device instrumented testing against actual firmware for pairing/reconnection/bonding, matching AGENTS.md's existing bar ("on-device integration tests for pairing and reconnection", "packet captures are the source of truth") — bonding races and real Android BLE stack quirks across OEMs are exactly what a mocked `BleManager` or fake GATT server would fail to catch faithfully. No new mock/fake-GATT infrastructure is added.
